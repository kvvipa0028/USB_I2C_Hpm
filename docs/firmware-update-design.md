# 本机 USB 固件升级与安全设计草案

日期：2026-11-06。状态：S0 可评审设计，尚未冻结 Flash 地址、镜像格式或安全配置；不表示 Bootloader、签名、加密或防克隆已经实现。

范围为 [PRD](../PRD.md) 的 FR-FW-02/03，以及 [P0 开发顺序](p0-development-order.md) 的 S0/S8/S9。本机升级不使用 UDS，不涉及目标 ECU。本文没有执行烧录、OTP 写入、生命周期改变或硬件操作。

## 1. 已核实的起点

本机 SDK 为 `1.13.0`，Git HEAD 为 `ccc5ec46`；下表的 SDK 路径均相对 `HPM_SDK_BASE`（由 `tools/env.sh` 设置）。这是核对时的本地源码事实，不保证其他安装包或芯片 ROM revision 行为相同。

| 依据 | 已核实内容 | 不能据此推定的内容 |
| --- | --- | --- |
| `boards/hpm6300evk/board.h` | EVK 配置 `BOARD_FLASH_BASE_ADDRESS=0x80000000`、`BOARD_FLASH_SIZE=16 MiB`、XPI0 | 正式产品 NOR 型号、容量、sector/page、写保护与掉电特性 |
| `soc/HPM6300/HPM6360/toolchains/gcc/flash_xip.ld` | SDK 默认 NOR 配置在 Flash+0x400、boot header 在 +0x1000、app 在 +0x3000 | 产品 Bootloader 的空间和最终 app 地址 |
| 同目录 `flash_dfu.ld` | 默认给 DFU Bootloader 预留 0x20000，应用起点随之改变 | 本项目可以不改 linker 就加 Bootloader，或第二槽可任意地址 XIP |
| `firmware/usb_i2c/build/build.ninja`（已有本地构建） | 当前 bridge 引用 `flash_xip.ld`，传入 `_flash_size=16M` | 该构建已包含升级、恢复或安全启动 |
| `samples/cherryusb/device/dfu/common/hpm_dfu_trigger.c` | 示例 `jump_to_app()` 检查 `BOARD_DFU_SIGNATURE` magic 后跳转 | magic 是密码学签名，或半写入镜像不会被启动 |
| `middleware/cherryusb/port/hpmicro/hpm_dfu_port.c` | 示例提供 NOR 读写/擦除接口 | 已有完整镜像验证、冗余元数据、原子提交和回退 |
| `samples/cherryusb/device/dfu/bootloader/README_zh.rst` | 示例 Windows 流程要求 Zadig | 可直接满足产品 app/恢复模式免驱 |
| `soc/HPM6300/HPM6360/hpm_romapi.h` | 有 EXIP 配置接口；区域 start/len 的接口注释要求 4 KiB 对齐 | ROM 安全启动链、设备密钥绑定、密钥不可导出和锁定后恢复已验证 |

因此只复用 SDK 的 NOR/USB/启动接口作为候选基础，不将 DFU 示例或 UID 当成 FR-FW-02/03 的完成件。

## 2. 最小责任划分

| 模块 | 建议职责 | 边界 |
| --- | --- | --- |
| 受保护 Boot/恢复入口 | 选择可启动镜像、验证信任链、执行受控安装/恢复、枚举恢复 USB | 普通 app 更新不能覆盖 Boot、密钥或板级不可变数据 |
| app | 接受进入升级请求、释放 I2C、报告版本/健康状态、完成试启动确认 | 不自行把接收完成标为安装成功，不决定信任根 |
| 更新状态机 | 接收分块、验证完整包、安装、试启动、提交；断电后恢复 | 每一步有确定的持久化边界，不以 RAM 标志代替落盘状态 |
| Rust 更新 API/CLI | 设备身份匹配、包预检查、状态查询、发送和结果分类 | 不自动重放未知状态的写入；先查询 update session/镜像摘要再决定后续动作 |
| GUI | 选择包、显示目标与版本、用户启动、进度与恢复提示 | 进度分别表示已接收、已验证、已安装；成功来自重启后设备确认 |
| 打包/生产工具 | 确定性编码、签名/加密、生产记录和受控 provisioning | 私钥/设备秘密不进入源码、普通日志或发布包 |

升级任务独占本设备：普通 I2C 请求立即返回明确的 busy/updating 结果，不排队到升级后执行。app 与恢复模式应通过同一设备身份关联；VID/PID/接口编号和 Windows 描述符在 USB 协议设计中登记，不能靠碰巧枚举的第一台设备继续升级。

本草案只定义更新语义，不分配线上命令号；命令编码交给统一 USB 协议登记表，保留既有 v1 和 UDS 规划命令空间。

## 3. Flash 分区：先定义用途，不冻结地址

推荐先验证“固定 app 执行地址 + 独立暂存 + 受保护恢复入口”。如果产品要求失败后自动回到旧 app，必须另保留旧有效镜像或证明 A/B 方案可行；只有恢复模式可用不能冒充已经实现 DEV_PLAN 所称的镜像回退。选型结论见 U02。

| 逻辑区 | 用途 | 写入者和约束 |
| --- | --- | --- |
| BOOT | 启动/恢复代码、必须的 ROM 启动结构 | 普通升级禁止写；保护机制和工厂维护路径待厂商资料确认 |
| APP | 固定地址运行的应用镜像 | 只由 Boot 在完整候选镜像验证后安装；安装未完成绝不启动 |
| STAGING | 完整升级候选包/镜像 | 接收阶段写此区；必须覆盖允许的最大包及头/签名/加密开销 |
| META_A / META_B | 独立擦除单元中的更新状态日志 | 新记录验证并提交前保留上一份有效记录；不能把二者放在同一擦除单元 |
| CONFIG | 产品配置/校准、必要的非秘密设备信息 | 与更新擦除范围隔离；迁移/保留规则必须写入版本合同 |
| ROLLBACK（若选用） | 上一份可启动镜像 | 空间与安全验证规则明确后才能承诺自动回退 |

布局审查使用符号预算，不先写入具体地址：

```text
N = 实际 NOR 可用容量
E = 实际擦除单元；P = 实际写入粒度/对齐
B = Boot 及 ROM 结构的保留空间
A = 允许的最大 app 存储镜像（含签名/加密格式开销）
S = 最大暂存包；M = 单份元数据区；C = 配置/校准区；R = 可选回退区
要求：B + A + S + 2*M + C + R <= N，各区满足各自 E/P/ROM/EXIP 对齐要求
```

`E/P`、容量和区域对齐不能从 EVK 容量宏猜测。最终地址表必须同时生成/约束 linker、Boot 白名单、打包工具和 host 包检查；优先维护项目自己的源输入，不手改生成的 map/bin。CI 增加分区不重叠、镜像超限失败、受保护区不可达检查。

固定地址方案在覆盖 APP 时不保证旧 app 仍完整，但必须始终有可运行的恢复入口和已验证 STAGING；安装完成后重新验证 APP。若 STAGING/APP 损坏或掉电状态无法确定，停在 USB 恢复模式。A/B 必须另验证映射/链接地址、ROM 验证和 EXIP 覆盖范围，不能把两个地址当成可互换槽。

## 4. 镜像与信任链合同

建议包头最少包含：格式版本、目标产品/硬件兼容范围、镜像版本、payload 长度、布局标识、payload 摘要、签名算法及 key id、必要的加密参数。具体字节编码、算法和算法参数待 U03/U04 冻结；`key id` 只用于选择已信任公钥，不能令包内自带公钥成为信任根。

必须满足：

1. 固定签名字节表示；签名覆盖安全相关头字段及 payload 摘要，不能只签数据而允许篡改目标、长度、入口或地址。地址必须落在 Boot 自己的安装白名单，不能由包任意指定。
2. 接收前验证有界长度与目标，接收完成后验证实际长度、完整摘要与密码学签名，再允许安装/标记待启动。错误目标、截断、溢出和未知格式均不得变成可启动镜像。
3. 每次启动都执行本方案规定的可信验证；更新元数据不能跳过它。元数据 CRC 只用于检测 torn write，不提供真实性。
4. 期望信任链为“已配置 ROM 信任根 → 可信 Boot → 可信 app”。ROM 实际支持的算法、镜像结构、恢复来源和验证范围，以对应 HPM6360 ROM revision 资料/官方工具确认；未确认前只可标“软件验签原型”。
5. 签名保障真实性，加密用于保密/设备绑定；两者分开设计和测试。原始 NOR 跨板不能运行，需要可信设备绑定或受保护的每设备秘密；公共 UID、同一通用签名或通用加密密钥不能单独满足该目标。
6. 开发测试密钥和生产信任根分离。设备密钥的生成、注入、不可读策略、发布包到设备密文的转换及返修流程，必须在不可逆 provisioning 之前评审并验证。
7. 恢复回退和防降级是不同要求。是否增加 anti-rollback、版本计数和密钥轮换由 U05 决定，不为本草案提前写 OTP。

Windows EXE/安装包签名属于发布流程，不能代替上述设备固件签名。

## 5. 更新状态与断电边界

以下为状态合同草案，尚无固件实现；具体元数据记录布局待 NOR 资料和故障模型验证。

| 状态 | 进入条件 | 重启后的规则 |
| --- | --- | --- |
| CONFIRMED | 当前 app 的可信验证、试启动确认和记录提交均完成 | 验证当前镜像后启动；显式恢复请求仍可进入恢复 |
| RECEIVING | update session、目标及长度检查通过，开始写 STAGING | 未完整验证的暂存镜像不能启动/安装；保留旧有效 app 或进入恢复 |
| VERIFIED | 暂存长度、摘要、签名、目标/布局全部通过 | 可开始安装；安装前仍校验所引用镜像与记录一致 |
| INSTALLING | 写 APP 前已持久记录“不可启动旧 APP/安装未完成” | 只恢复安装或进入恢复，不能从写到一半的 APP 跳转 |
| TRIAL | 完整 APP 验证后写入试启动记录 | 有界试启动；没有 app 确认时按所选回退方案处理，否则进入恢复 |
| RECOVERY | 无可信镜像、元数据歧义、安装失败或显式进入 | USB 可重新接收可信包；不绕过验签，不要求 JTAG 才能恢复 |

元数据包含格式、generation、状态、update session、目标/布局、候选摘要/长度、安装进度和试启动计数；不存秘密。建议采用追加记录、冗余擦除单元、CRC 和最终提交标志。必须按实际 NOR 的允许编程次数和掉电行为验证；**不假设单次 page program 或 commit word 天生原子**。掉电后只认完整且自洽记录，generation 回绕/冲突有明确规则；记录指向的镜像仍需独立可信验证。

试启动次数、确认 deadline、完成判据和恢复超时由 U06 冻结；app 不能仅在刚进入 `main()` 时确认，应完成规定的版本/关键初始化自检。写 Flash 时同一 XIP 器件的取指、cache、向量/ISR、USB 响应和 watchdog 需要明确的 RAM 执行边界及最坏时间预算。

host 超时/掉线后报告“状态未知”，重连只查询，不重放上一写入。仅当设备确认同一 session 和已验证的块/镜像位置后，才能按冻结协议显式继续；不支持续传时重新开始一个受控更新，不拼接不同包。

## 6. 验证分层与准入

| 测试 ID | 无板可准备/执行 | 必须上板的证据 |
| --- | --- | --- |
| UPD-01 包检查 | 格式、长度/整数溢出、布局、目标、篡改/坏签名、未知 key/算法的测试向量 | Boot 与 host 对同一包给出一致判断，保护区不可写 |
| UPD-02 状态恢复 | 在每个逻辑写步骤注入截断/损坏/旧记录，模型只能选可信 app 或恢复 | 实际 NOR 在擦除、写入、校验、元数据提交、首次启动窗口中断 |
| UPD-03 USB 恢复 | host 状态机、设备身份匹配、busy、未知结果、无盲目重发 | app 损坏后恢复 USB 可用；全新 Windows 10/11 app/恢复模式均免驱 |
| UPD-04 成功闭环 | GUI/API 成功条件测试：发送完成不足以成功 | 重启后设备实际版本、镜像验证、健康确认一致 |
| SEC-01 可信启动 | 签名负向向量、工具可复现性、配置审查 | 对应 ROM/生命周期中未签名、坏签名、错根、篡改密文不启动 |
| SEC-02 防克隆 | 原始 NOR 复制实验设计和记录模板 | A 的原始 NOR 复制到未授权 B 不能运行；A 可正常升级；不同绑定参数的已配置板也覆盖 |
| SEC-03 生产恢复 | provisioning 顺序、异常路径和返修流程评审 | 锁定后允许的签名升级/恢复、debug/readout 策略均符合方案 |

FR-FW-02 必须做至少 20 次升级中断且全部可恢复，覆盖上述五种窗口，分别区分仅 USB 断开和实际断电。每次保存版本、包摘要、断点、重启选择和恢复日志；使用 JTAG 重刷不计产品恢复通过。先在未锁定开发板验证，再在最终 EVT NOR/供电上复验；安全锁定后的合法恢复另有 SEC-03 证据。

FR-FW-03 的 OTP/生命周期实验仅在指定牺牲板和对照板执行，不在日常 EVK 上试烧。本文不授权这些操作。模型通过、编译通过、SDK 字段存在均不能关闭硬件验收。
